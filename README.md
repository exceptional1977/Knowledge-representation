# Прототип базы знаний модуля объектно-центрированной процессной аналитики

Семестровый проект по дисциплине «Представление знаний в киберфизических системах»,
МГТУ им. Н.Э. Баумана, кафедра ИУ12, группа ИУ12-31М, И.С. Бронников.

**Граница объекта.** Модуль объектно-центрированной процессной аналитики решает для
бизнес-аналитика и ML-инженера задачу прогнозирования временных KPI экземпляров
бизнес-процесса моделями XGBoost и GNN и выявления риска нарушения SLA в процессе
предиктивного мониторинга бизнес-процессов организации по журналам событий OCEL 2.0.



Код приложения написан с помощью языковой модели (Claude), как допускается разделом 8 задания, поэтому основная часть проекта закоммичена одним блоком 20.10.2026 (коммиты КТ1–КТ5). Предметная область, граница объекта и исходный состав понятий взяты из НИР.



## Установка и запуск (одна команда)

Нужен Python 3.10+.

```bash
pip install -r requirements.txt
python run.py            # затем открыть http://127.0.0.1:5000/
```

Параметры: `python run.py --port 8080`. Кнопка «Исходная база» в шапке возвращает базу
знаний к состоянию из `kb/seed` (перед демонстрацией).

## Что где лежит

|Путь|Содержимое|
|-|-|
|`kb/seed/\*.ttl`|исходная база знаний: 6 именованных графов в Turtle|
|`kb/current/\*.ttl`|рабочая база (создаётся при первом запуске, сохраняется после каждого изменения)|
|`kbapp/store.py`|хранилище: rdflib `Dataset`, именованные графы, загрузка/сохранение, журнал|
|`kbapp/semnet.py`|семантическая сеть: словарь отношений, карточка с наследованием, BFS/DFS, SPARQL, проверка|
|`kbapp/frames.py`|фреймы в RDF: AKO, наследование U/S/R/O, SHACL (pySHACL), ризонер owlrl|
|`kbapp/procedures.py`|демоны IF-ADDED / IF-REMOVED / IF-NEEDED и присоединённые процедуры|
|`kbapp/rules.py`|продукции на SPARQL Update, прямой и обратный вывод, конфликты, объяснение|
|`kbapp/scenario.py`|исполнение фреймов-сценариев по шагам|
|`kbapp/rebuild.py`|перестроение обеих моделей по 7 шагам (раздел 11 задания)|
|`kbapp/mapping.py`|соответствие моделей и список расхождений|
|`kbapp/viz.py`|рисование графов в SVG|
|`web/`|Flask-приложение: 4 экрана + панель «Что изменилось»|
|`tests/kb\_report.py`|сводка для пояснительной записки → `out/report.json`|
|`tests/demo\_protocol.py`|протокол перестроения через интерфейс → `out/protocol.md`, `out/screens`|

Именованные графы: `semantic`, `frames`, `data`, `shapes`, `rules`, `scenarios`, `inferred`,
`runs`, `journal` (IRI вида `http://bmstu.ru/iu12/ocpa/graph/<имя>`).

## Пример сессии

1. **Семантическая сеть** → «Добавить вершину»: «Платёжный документ», группа «Информационные
объекты», связь «является → Бизнес-объект». Связь проверяется по словарю отношений,
вершина подсвечивается, в панели справа — предложение создать фрейм → «Создать фрейм».
2. **Фреймы** → класс «Кейс кредитной заявки» → «Создать экземпляр». Без слота «Журнал»
SHACL не даст сохранить. С полными данными: наследуется норматив SLA, ризонер относит
кейс к родительским классам, демон IF-ADDED пересчитывает среднее ожидание, вывод
выдаёт риск и рекомендацию.
3. **Сценарии** → «Запустить», выбрать кейс Application\_1001, «Шаг» до сцены 5. Затем во
«Фреймах» у HeteroGNN v1 изменить «Индекс дрейфа» на 0.27: срабатывают R25 → R26,
GNN выключается, прогноз берётся у XGBoost, риск становится умеренным, и сценарий
переходит в ветку «6а. Усиленный контроль».
4. **Правила и вывод** → «Запустить прямой вывод», «как получено?» у решения, проверка
гипотезы для нового кейса (система спросит недостающие слоты), «выгрузить трассу».

Повторить весь протокол автоматически (при запущенном приложении):
`python tests/demo\_protocol.py --port 5000` (снимки экранов — если установлен playwright).

## Что программируется самостоятельно

Поиск в ширину/глубину, наследование значений по умолчанию, демоны, цикл применения
правил с разрешением конфликтов, обратный вывод, исполнение сценариев и объяснение
написаны в проекте. Библиотеки: rdflib (граф, SPARQL), owlrl (вывод принадлежности
классам), pySHACL (проверка), Flask (интерфейс), networkx (только раскладка вершин рисунка).

## Ограничение прототипа

Процедура `predict\_forecast` вместо обращения к обученным моделям ML-/GNN-модуля ВКР
вычисляет прогноз детерминированной функцией признаков кейса с коэффициентами из фрейма
модели. Метрики HeteroGNN v1 в `data.ttl` — плановые и уточняются в НИР-3.
